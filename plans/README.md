## Findings deliberately not turned into immediate implementation plans

- Browser automation / attach to personal Chrome: defer until a concrete browser task justifies its credential, page-content and action-approval surface.
- Desktop app, sidecar, HTTP remote access and Telegram/Discord: defer because the product is explicitly terminal-first and these introduce new control/identity boundaries.
- Scheduled/overnight autonomy: defer; interactive goal mode and verification currently fit the project scope.
- Managed local model lifecycle: defer; external OpenAI-compatible local endpoints keep the runtime small and model backend-agnostic.
- Plugin marketplace and broad plugin ecosystem compatibility: defer; standard Agent Skills, local declarative plugins and MCP already cover local extensibility.
- Parallel subagents: defer until process cancellation, resource limits, approval ownership and real-repository evaluation are stronger.
- Document parsing/media generation/desktop control: do not add for parity alone. Add a dedicated tool only when repeated personal coding workflows require it.
- GAIA score parity: rejected as a proxy for coding-agent quality; prioritise verified changes on reproducible real project tasks.

## Vercel architecture constraints

- Vercel Sandbox is remote compute, not local execution. Source code, commands and selected environment values sent to it leave the workstation; remote execution requires explicit consent and a visible project/region/network policy.
- Keep local execution and SQLite as defaults. Vercel dependencies must be optional.
- Preserve the existing Linux Bubblewrap fail-closed behavior for MCP stdio. Vercel Sandbox is a separate opt-in backend, not an implicit fallback.
- Vercel deployments should target a Git-connected Vercel project and an already pushed commit. Do not silently commit/push, deploy dirty worktrees, create projects, change domains or promote production.
- Relational database integrations are provisioned through the Vercel Marketplace (for example, a PostgreSQL-compatible Neon or Supabase integration); they are not a first-party Vercel-managed relational database product. Use generic PostgreSQL connectivity and leave provider choice to the maintainer.
- Vercel Blob is object storage for bounded immutable artifacts, not a transactional database or a network filesystem for the live SQLite database.
- Cloud session storage and Blob uploads transfer private prompts, tool outputs, project metadata or artifacts. Keep sync off by default, require explicit consent and provide retention/deletion controls.

## Dependency notes

- Plan 009 precedes 010; 011 and 012 can proceed independently.
- Plans 010–012 must keep remote actions opt-in and must not change local-first defaults.
- Live provider, Vercel Sandbox, deployment, PostgreSQL and Blob integrations must not run in routine PR CI. Use mocks/fakes; gate live tests behind explicit environment flags.
- The old Plan 007 is complete: PRs #43–#46 were merged to main on 2026-11-14 and their lightweight CI checks passed.

## Findings considered and rejected

- **Replace SQLite with cloud storage by default:** rejected. It would contradict the product's local-first behavior and create unnecessary account/network dependencies.
- **Use Blob as a session database or SQLite filesystem:** rejected. Blob is object storage; transactional session records belong in PostgreSQL if the maintainer opts into a cloud database.
- **Auto-deploy local dirty worktrees:** rejected. A Git-connected deployment must identify a pushed source revision; local changes must not be misrepresented as deployed.
- **Replace Bubblewrap with Vercel Sandbox automatically:** rejected. MCP sandboxing has an explicit fail-closed local security contract; remote execution must be a separately selected backend.
- **Upload all existing SQLite history automatically:** rejected. Cloud migration requires an explicit dry run, data minimization, confirmation, and a way to export/delete.
